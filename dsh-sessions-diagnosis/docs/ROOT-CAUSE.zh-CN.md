# 根因：为什么 DSH 升级后有些会话打不开了

本文说明本插件所诊断并修复的故障。内容基于已安装的 DSH 0.1.5-rc.2 包写成——既阅读了随包发布的代码，也用它跑了真实的会话日志。

## 现象

升级 DSH 之后，有些对话从侧边栏里“够不着”了：它们仍然列在那里，但点进去看到的不是历史记录，而是一个加载错误。安装本身的其它方面看起来都正常，而且出问题的会话并不都是最新的那些。

在 Web UI 中，报错信息是：

```
Failed to load history: failed to observe session "<id>":
cannot safely transform unclassified message source; source v0 artifact remains unchanged (raw log: <...>\session.jsonl.zstd)   (gateway/internal)
```

## 存储模型

DSH 把一个会话存储为一个目录，其中**每一个不可变的格式代（generation）对应一个文件**：

```
$DSH_HOME/sessions/<project>/<session-id>/
    session.jsonl.zstd          # 第 0 代（v0 不带 .vN 后缀）
    session.v3.jsonl.zstd       # 第 3 代（当前格式）
```

- 当前的格式版本是 **3**。
- 运行时操作总是选取**编号最大**的规范代；而一个目录里如果同时混有压缩代和非压缩代，会被直接拒绝。
- 一个物理文件是**若干个相互独立、各自带校验和的 Zstandard 帧的拼接**：第一帧恰好只放 JSON 头行，之后的每一帧放一批持久化追加的 JSONL 行。

由于各代是不可变的，格式升级并不会改写旧文件。它是在**打开时惰性迁移**，并把后继代发布在原始文件**旁边**。原始文件永远不会被改名、重写或删除。

关键在于，后继代只在**写入**方式的打开中才会发布：

| 打开方式 | 会发生什么 |
|---|---|
| 读取 | **在内存中**解码并迁移，返回历史记录，不写任何文件 |
| 写入 | 执行同样的迁移，然后发布 `session.vN.jsonl.zstd` |

所以，存在 `.v3` 兄弟文件意味着“这个会话在升级之后被以写入方式打开过”。对于一个你只是看过一眼的会话来说，它不存在是正常的——**除非**迁移本身失败了。

## 故障

迁移会沿着相邻链 `v0 → v1 → v2 → v3` 逐级前进。最后一条边 V2→V3 并不是一次重新格式化，而是一次**封闭词表审计**。每一个 message 槽位都必须携带一个取自固定十五个取值的 `source.kind`：

```
user, plugin, model, tool, agent-instructions, session-reference, team-message,
goal, skill-invocation, skill-catalog, coordinator, subagent-report,
subagent-settled, webhook, agent-message
```

任何其它取值都会中止**整个**迁移：

```
SessionFormatUnsupportedMigrationError: cannot safely transform unclassified message source
```

只要有一个已被废弃的取值，就足以让整段对话无法打开。实际见到的那种取值是 `at-file-mention`：

```json
{
  "type": "user/message",
  "seq": 10,
  "data": {
    "content": [{ "type": "text", "text": "<workspace-reference path=\"docs/notes.md\" kind=\"file\" />" }],
    "source": { "kind": "at-file-mention", "relative": "docs/notes.md" },
    "role": "user",
    "id": "..."
  },
  "surfaceOp": "append"
}
```

这条记录是旧版本在有人在输入框里打出 `@path` 时发出的合成用户消息。字符串 `at-file-mention` 在 0.1.5-rc.2 的各包中已经无处可寻——词表条目被直接删掉了，而审计里没有任何规则能映射它。

这就解释了为什么这种损坏看起来毫无规律：它精确地影响那些曾经有人用过 `@` 提及的会话。从没用过的会话仍能顺利迁移，更早的对话也可能继续正常工作。

### 第二种互不相关的拒绝

另一个陈旧的取值会在更早的 `v0 → v1` 这条边上产生不同的报错：

```
SessionFormatUnsupportedMigrationError: subagent/descriptor <seq> uses unsupported descriptor version 2
```

已发布的 v0 载荷编解码器要求 `subagent/descriptor.data.version` 必须恰好为 `3`，而描述符的结构是由它的 `mode` 成员决定的——并非由 `version` 决定——所以陈旧的版本号只是一个元数据缺陷，而不是结构性缺陷。

### 迁移失败后会留下什么

什么都不会留下。源代保持逐字节不变，不写后继代，暂存文件也会被删掉。这对安全是好事，对诊断却是坏事：唯一的证据就是那个异常，而它在往上几层就被吞掉了，最终渲染成一条笼统的网关错误。

## 用户可见的错误链

```
session-persistence-jsonl  抛出 SessionFormatUnsupportedError
                           "<reason>; source v<N> artifact remains unchanged (raw log: <path>)"
        ↓
session-query              包装为 SessionQueryError，
                           code 为 SESSION_QUERY_PERSISTENCE_FAILED
        ↓
api-session-controller     没有针对该 code 的映射
        ↓
api-gateway                把它归并为 RemoteError('gateway/internal', message)
        ↓
client-ui-chat             渲染成 "Failed to load history: <message> (gateway/internal)"
```

注意，原始日志路径**确实**一路传到了 UI——这通常就是你找到那个文件（随后由本工具诊断）的方式。

## 修复原则

由于各代不可变、发布是增量式的，正确的修复方式**不是**去编辑历史，而是做 DSH 自己会做的事：产出一个有效的后继代，让 DSH 去选它。

```
解码旧代
  → 对一份内存中的副本施加最小规则改动
  → 在打过补丁的行上重新运行 DSH 真正的迁移
  → 用 DSH 自己的当前格式编码器编码结果
  → 重新读取编码后的字节，证明它们能通过存储层的结构准入检查，
    并且能完成一次完整恢复
  → 把 session.v<N>.jsonl.zstd 发布到原始文件旁边，不覆盖任何东西
```

这给你带来如下性质：

- **源文件永不被修改。** 只要删掉发布出来的后继代，修复就可撤销；原始文件始终可作为回滚来源。
- **未经验证可用的东西一律不写入。** 如果某条规则猜错了，校验就会失败，于是不会有任何文件出现。
- **改动是最小的。** 不新增、不删除、不重排任何事件，因此序列坐标、时间戳和交叉引用都原封不动。`@` 提及的路径也没有丢失——它本来就逐字记录在该消息自身的内容里，被丢弃的只是一个冗余的来源标签。

## 两个值得知道的坑

这两个都是在本项目构建过程中踩出来的，而当你自己写工具时也很容易掉进去。

### 1. DSH 的恢复流程会改动你交给它的那些行

格式库的文档写明，恢复会“把调用方拥有的已解析值穿过有状态的各个阶段，**中间不复制工件、也不冻结**”。因此它会修改交给它的行对象——**包括在它中途失败的时候**。

于是，把同一个数组喂给第二次恢复会得到一个**错误答案**，通常是一个幽灵般的报错，例如：

```
SessionFormatError: released Session row 16 has seq gap (expected 170, got 37)
```

事件本身毫发无损；只是第二次恢复看到的是半转换状态的数据。一个天真的工具如果在同一个数组上探测、打补丁、再探测，就会理直气壮地把一个可修复的会话报成损坏。

本插件探测的是一份防御性副本，绝不改动调用方的行。有一条回归测试专门钉住这一行为。

### 2. 绝不要承诺一个你尚未证明的修复

一份日志可能同时带着两个互不相关的缺陷，而第二个只有在第一个被修好之后才会暴露出来。仅凭“有规则匹配”就报告“可修复”，是一种用户只有在授权写入之后才会发现的谎言。

所以诊断会**先在内存中模拟修复**，只有当修复后的日志确实被证明可以迁移时，才会报告 `repairable`。若不能，结论就是 `unrepairable`，并改为报告残留的错误。

## 失败分类

| 结论 | 含义 | 该怎么办 |
|---|---|---|
| `ok` | 被选中的代已是当前格式，且能干净地恢复 | 无需处理，直接打开 |
| `unmigrated` | 仍是较旧的一代，但迁移顺利，能正常打开 | 无需处理；以写入方式打开该会话时，DSH 自己就会发布当前格式的后继代 |
| `repairable` | 迁移被拒绝，有已知规则匹配，**并且**已验证修复后的日志可以迁移 | 运行 `dsh-session-doctor repair <id>`（先 dry run），或在面板里点**修复** —— 同一个两步流程 |
| `unrepairable` | 迁移被拒绝，且要么没有规则匹配，要么修复后的日志仍然失败 | 保留日志，并连同诊断给出的原因码一起反馈；本工具不会为它臆造自动修复 |
| `corrupt` | 物理字节已损坏：帧魔数错误、校验和失败、行无法解析 | 若有自己的备份就从备份恢复 —— 本工具修的是**格式**，不是损坏的字节，也不会去猜 |
| `too-new` | 由比本工具更新的 harness 写入 | 升级 DSH，而不是把日志降级 |
| `empty` | 不存在任何规范代 | 检查 harness 是否指向了你以为的那个会话库（`DSH_HOME`），以及是否是备份或清理留下的空目录 |
| `unknown` | **什么都没检查**：当前这份 DSH 没有 `@deepseek-ai/dsh-session-format-catalog`，借不到它的迁移链来检验日志 | 这既不是失败，也不是对日志的结论 —— 请换一份带该编解码器的 DSH 安装（0.1.3-alpha.2 及以上）再扫描。这里的 `openable: false` 只表示"未被证明"，所以每份报告都把 `unknown` 与"打不开"的会话分开列出 |

## 修复安全吗

诚实的回答分两部分：哪些是由构造方式保证的，哪些只是因为被检查过才得以保证。

### 由构造方式保证

修复绝不编辑源代。它在旁边发布新的一代——与 DSH 所做的增量式发布完全一致——因此修复前的字节原封不动地留在磁盘上，DSH 自身的保留策略也得以维持。本工具中没有任何东西会删除会话日志。

### 因为经过检查才得以保证

除非下列各项全部成立，否则修复会被拒绝：

| 检查 | 为什么需要它 |
|---|---|
| 打过补丁的日志能在 DSH 真实的迁移链下迁移 | 这正是修复的意义所在 |
| 结果能用 DSH 自己的当前格式编码器编码 | 手写的编码器可能在细微处出错 |
| 字节能被重新读出并通过结构准入 | 这是存储层自己的恢复前关卡 |
| 在**两种**校验策略下都能完成完整恢复 | 捕捉仅靠准入关卡会放过的那些问题 |
| **每一个源消息载荷都出现在结果中** | 结构有效并不意味着对话幸存了下来 |

最后一条值得强调。一次迁移可能产出一份完全可读、却悄悄丢掉了消息的日志，而一个只问“它能加载吗？”的检查会把它判为成功。逐条比对消息载荷，才把“你的对话被保留了”从一句假设变成了一个实测量。

在真实会话上的实测：分别有 248 个和 643 个源载荷，**零丢失**，且恰好只多了 v2→v3 规范所要求的那两条 `system/message` 新增（一个空的开头，以及从请求头中提升出来的 prompt）。

### 撤销一次修复

修复是可逆的，而反向操作被刻意做得范围很窄。每次修复都会写一个 sidecar 文件，记录两个文件的 SHA-256；而 `rollback` 会：

1. 如果被选中的代不是记录所描述的那一代，或者它的字节自那以后发生了变化，就拒绝执行；
2. 否则把它以非规范文件名**挪到一旁**，于是 DSH 不再选中它，会话回到修复前的状态。

第 1 步才是关键。每当你在 DSH 中恢复一个会话，DSH 都会向当前代追加内容，因此一个在修复之后又被写入过的后继代，此时承载着别处不存在的历史。删掉它就会毁掉那段历史。拒绝是唯一正确的行为，而本工具正是这么做的。

第 2 步让回滚本身也可逆：文件只是被移动，从不会被删除。

### 原子性

发布时会先暂存一个完整文件、刷盘，再用硬链接把它放到目标位置，因此并发的读者要么看到完整的一代，要么什么都看不到。在不支持硬链接的文件系统上，独占复制的回退方案会拿暂存的字节做校验，不一致时就把副本删掉——因为写了一半的代比完全没有代更糟：DSH 总是选编号最大的那一代，所以一个损坏的后继代会把一个尚可读取的前驱代藏起来。

## 方法

上面每一条论断都是对照已安装的包验证过的，而不是从行为反推出来的：

- `@deepseek-ai/dsh-session-format` —— 规范文件名规则与代号解析
- `@deepseek-ai/dsh-session-format-catalog` —— `currentVersion: 3` 以及组合起来的 v0→v3 链
- `@deepseek-ai/dsh-session-format-v2-to-v3` —— `SOURCE_KINDS`、`assertSource`、载荷审计
- `@deepseek-ai/dsh-session-format-v0-to-v1` —— `subagent/descriptor` 的版本规则
- `@deepseek-ai/dsh-session-persistence-jsonl` —— 代的选择、帧容器、发布路径

诊断流程运行的就是这同一套 catalog。它的结论不是对 DSH 规则的重实现；它们**就是** DSH 的规则，被真的执行了一遍。
